# 发布前材料检查与待办

## 1. 当前不能直接宣布“已经开源发布就绪”

本轮只做本地候选材料检查，不初始化 Git、不创建远程仓库、不上传内容。

**仍有两类人工门槛：** 整个应用的许可证尚未选择；用户还需要确认没有不应公开的原创/私有内容。自动扫描不能代替版权、来源和隐私授权判断。第35步演示由用户负责，真实模型成功证据也尚未具备。

## 2. 候选发布范围

本轮使用显式白名单，而不是把整个工作目录压缩上传：

| 包含 | 用途 |
| --- | --- |
| `src/` | 应用源码、包内迁移、数据登记和维护者验收 |
| `tests/` | 无模型测试、集成测试和明确标记的替身设施 |
| `sandbox/` | 固定 Dockerfile 和测试依赖锁 |
| `benchmarks/` | 合成任务、参考材料、来源审阅与范围明确的许可 |
| `docs/` | 架构、使用、证据、边界与学习材料 |
| `.github/` | 不依赖模型密钥的 CI 配置 |
| `README.md`、`pyproject.toml`、`uv.lock` | 入口、元数据、依赖版本 |
| `.python-version`、`.gitattributes`、`.gitignore`、`compose.yaml` | 解释器、换行、忽略和本机数据库配置 |

复制时还需在这些目录内排除 `__pycache__`、测试/格式缓存、链接和任何新增的本机配置。源码副本逐文件 SHA-256 应与白名单源材料一致。

**不包含：** `.venv/`、`.patchpilot-runs/`、`.patchpilot-service/`、`.patchpilot-evals/`、`.env` 及其变体、本机 SDK/CLI 凭据目录、`.claude/` 的本机配置、`dist/`、数据库文件或卷、浏览器状态、下载缓存。已有 `.gitignore` 不是完整的安全边界；它不覆盖未来所有命名，也无法阻止手工打包、强制添加或发布曾经提交过的秘密。

当前没有 Git 历史，所以没有“已扫描历史提交”的结论。将来初始化 Git 后，发布前需要复查实际暂存清单，而不是只信工作区的忽略规则。

## 3. 密钥和隐私检查

本轮对候选文本做有限模式扫描，包括私钥头、常见 API Key / GitHub token / AWS key、字面 Bearer、带凭据 URL 和敏感字段赋值；只输出命中规则、路径、行号和摘要，不复制秘密值到报告。

初次扫描的待核查命中是两个集成测试中相同的公开测试令牌：

- [tests/test_live_service.py](../tests/test_live_service.py) 的 `live_service`。
- [tests/test_service_cli.py](../tests/test_service_cli.py) 的独立诊断 Worker 测试。

两者都是测试构造的本机 API 认证值，不是实际用户令牌或模型凭据。固定数据库 URL 中的公开开发密码也按[服务指南](stage4-service.md)单独记录，不隐瞒它包含密码字段；该值只适合受控本机，不能当生产密钥。

最终扫描范围、数量与结果见[本轮证据](phase6-progress.md)。**未检出已知模式的真实密钥不等于数学证明无秘密**：未知格式、编码/拆分值、自然语言私人信息和未来改动仍可能漏过。

发布前还需用户人工检查：

- [ ] 没有个人 API 认证、会话 cookie、数据库真实凭据或客户连接串。
- [ ] 没有课程/实习/公司未获公开授权的代码、日志、Issue 或截图。
- [ ] 没有真实用户数据、内部域名、私有仓库链接或不应披露的本机路径。
- [ ] 若挑选运行结果作为公开证据，已单独脱敏并保留失败与未知成本；不是直接上传整个运行目录。
- [ ] 如果发现曾经暴露的真实密钥，先撤销/轮换；仅删文件或加 `.gitignore` 不够。

不要为扫描项目而把本机凭据内容发给第三方服务，也不要打印所有环境变量。

## 4. 来源与许可

### 自建基准资料

20项任务在 [dataset.json](../src/patchpilot/evaluation/dataset.json) 声明为 AI 协助自建合成场景，并非从真实用户 Issue 抓取。任务、快照、参考补丁和对应维护者验收的 MIT 范围由 [benchmarks/LICENSE](../benchmarks/LICENSE) 明确列出。

可执行红绿验证不能证明所有合同合理，仍需用户审阅 [benchmarks/REVIEW.md](../benchmarks/REVIEW.md)。不声称训练无污染或第三方独立审定。

### 应用及文档

根目录尚无覆盖整个应用的 LICENSE，`pyproject.toml` 也没有选择全局许可。**不能把基准 MIT 推广成整个应用已采用 MIT。** 用户需在确认代码权属后决定应用及文档的许可范围，再更新根 LICENSE、包元数据及说明；本轮不替用户作法律授权选择。

因此“未发现额外下载的外部源码文件”不能简化成“所有材料均已满足开源许可”。全局授权缺口是明确待办，不是扫描可以绕过的项目。

### 第三方依赖与容器

通过 `uv.lock` / 镜像依赖锁安装官方 SDK、Web/DB 库、测试与构建工具，候选源码不直接打包虚拟环境中的第三方实现。干净环境可以用 `importlib.metadata` 查看每个已安装发行包的 License-Expression、License/Classifier 和许可证文件；这只是清单，不是法律兼容性结论。

wheel 构建和依赖安装也不代表已完成镜像重分发审查。将来若发布 wheel、容器或捆绑依赖，应核对各依赖和基础镜像的通知、许可证与分发义务；不要因锁定 digest 就默认许可或安全性已被验证。

## 5. 将来的发布门

下面不是本轮已经执行过的动作：

1. 确认全局代码与文档权属，选择并补全许可证；必要时取得原权利人授权。
2. 人工核查实际候选文件与选定的演示/结果证据；真实模型与替身结果清楚区分。
3. 初始化 Git 后复查暂存文件及秘密扫描；确认没有把本机产物加入历史。
4. 在真正远程仓库实跑 CI；本地通过不能改写成 GitHub Actions 已通过。
5. 最后才根据用户明确授权提交、推送或发布。发布到外部服务是公开动作，不能由“文档写好了”自动推出授权。

## 6. 现在可以诚实地怎样描述

可以说“已实现受控工具、独立验收、可靠本机任务后端与可审计评测设施，并完成限定条件下的本地复现”。

不能说“已验证模型修复成功率”“优于基线”“恶意代码安全沙箱”“任意崩溃无损续跑”“全项目开源许可已齐全”或“远程 CI 已绿”。用户个人讲解能力也必须由用户完成自测，不由助手代签。
