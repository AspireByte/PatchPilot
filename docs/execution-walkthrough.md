# 个人讲解：追踪一次工具请求

这不是需要背诵的面试答案。目标是用**代码位置、请求/结果编号、工作区变化与测试证据**，解释一次实际执行；再关掉文档复述。本文不包含由用户自行负责的第35步演示制作。

先完成[无模型复现](reproduction.md)。脚本替身只能提供运行时链路证据，不能代替真实模型决策证据。

## 2. 核心问题的可核对骨架

> 某次工具请求怎样产生、校验、执行、记录，并影响下一轮决策？

选择一次 `apply_patch`，对照源码与自己的记录填写：

1. **产生：** 上一轮公开观察是什么？完整 assistant 响应中这个 `tool_use` 的 ID、名称和参数是什么？真实模型会选择工具，但本轮复现的选择来自测试替身，必须指出这个差别。
2. **响应级检查：** 完整 JSON 是否校验？`stop_reason`、工具 ID、预算/取消检查是否允许进入工具循环？为何不能收到半段补丁就执行？
3. **单工具检查：** `dispatch` 如何验证工具名称和 Pydantic 参数？路径策略、可修改文件和 `expected_hash` 分别在哪里检查？参数合法为什么还不能直接写文件？
4. **执行：** 修改发生在哪一份 repo？为何先在 staging 使用 Git 检查？发布用了几次 rename，这能保证什么、不能保证什么？
5. **记录：** `tool_started`、本地工具 JSON、`tool_finished`、transcript 各在哪里写？若物理修改后、证据或 checkpoint 提交前崩溃，哪些东西可能不一致？
6. **观察：** 如何使用相同 `tool_use_id` 构造 `tool_result`？同一轮多项结果怎样合并？哪些内容因限长只给预览，完整有界证据在哪里？
7. **下一轮：** 新的 user 消息怎样进入下一次 `complete`？失败观察可能让模型重新读取，但观察中的文字为什么不能改变运行时权限？脚本替身只能证明观察被传递，不能证明真实模型怎样理解它。
8. **结束：** `end_turn` 为什么不直接意味着通过？哪一层重新建立工作区，验收哪些测试，最后结论绑定哪些 hash？

注意三个容易讲错的顺序：

- 响应级协议检查在工具执行前；但工具参数是逐项验证，不是先验证整批再原子执行。
- 本地记录、服务 Step/Event 与 checkpoint 不构成一个覆盖物理工具执行的事务。
- 正常完成且未停止的工具批次才提交代码边界；不是每个工具都能无损恢复。

## 4. 从 CLI 扩展到服务层时再加四个问题

参考[服务指南](stage4-service.md)，不要把两层记录混在一起：

1. API 创建 Run 后为何立即返回 queued，而不是在请求里完成修复？
2. Worker 的租约 token、当前 Attempt 与数据库时间如何阻止旧 Worker 发布迟到结果？它们为何不能撤销一个已经发出的模型请求？
3. 最终报告、终态和终止事件在哪个 DB 事务里提交？为何文件已封存、DB 回滚时仍可能留下孤儿文件？
4. checkpoint 恢复为何建立新工作区、新模型会话与预算？测试已执行但未登记时为什么宁可重跑，不声称 exactly-once？

不要求为了练习启动付费 Worker；已有测试可帮助定位对应不变量。服务集成需要 PostgreSQL 的显式开关，不能因为普通测试跳过了就说已经亲自验证过。

## 5. 合上文档后的自测

建议先用几分钟讲一条完整执行，再尝试回答下面的问题；遇到卡顿回源码定位，不用背生成的段落。

- 相同源码下重复读文件为何会被重复行动机制停止？修改版本后为何可能不同？
- `read_file` 返回的摘要为什么不能被当成“允许写任意文件”的令牌？
- 一轮先成功改文件、后收到非法工具参数，工作树会整体回滚吗？
- 单次输出 token 上限与整次执行费用硬上限是同一个概念吗？usage 丢失还能说免费吗？
- 原测试全跳过、模型自己写的测试全绿，能否证明修复通过？
- 维护者验收没交给模型，为什么仍不等于对恶意 Python 保密？
- 完成提交之后到达的取消，能不能把已经发布的历史结论倒转？
- 预算停止的 completed/not_run，为什么不能直接按 failed/interrupted 的 restart 逻辑处理？
- 固定20项材料通过，与真实模型20项修复成功差在哪里？
- 如果一次生成更便宜且同样成功，项目还应该声称 Agent 更优吗？
