# 架构、取舍与可信边界

## 本地交互模式

项目新增独立的 `patchpilot chat` 路径：CLI → `AgentSession` → Anthropic 模型 → `LocalTools` → 同一会话继续输入。`GoalController` 仅在显式设置目标后，在合法回答结束处通过无工具的评估调用决定完成、暂停或继续。工作请求与评估共享当轮预算，使用量分别累计。

会话记录通过 `SessionStore` 独占打开并原子替换保存。恢复时保留历史与目标，但暂停执行、清空文件读取授权、为未完成工具补充中断结果；不重新执行旧命令。文件修改前保存原内容并校验摘要，差异不依赖 Git。

这是直接操作用户指定仓库的本地开发模式；授权的命令在宿主执行。它与下述固定任务、Docker、隐藏验收和服务端 Worker 路径分开，不将目标评估当作独立验收。CLI 无需数据库或 Docker；第一版无后台任务、网页或自动上下文压缩。使用方式见 [README](../README.md#本地仓库持续对话)。

## 1. 原受控任务模式解决什么问题

PatchPilot 接收**预先登记的小型 Python 任务快照与公开 Issue**，让一个模型通过受控工具尝试修复，输出候选补丁、执行证据与独立验收结论。它不是任意仓库的通用 Coding Agent，也不接受任意命令、仓库 URL 或宿主路径上传。

选择这个范围的原因：

1. 固定源码、环境、复现与验收，才能区分修复失败、环境失败和模型服务失败。
2. 小型 Python 仓库能把复杂度集中在 Agent 后端：工具契约、预算、状态、执行隔离、取消、租约和恢复，而非包管理与跨语言构建。
3. 目标是能解释每一次动作为何允许、如何执行、证据在哪里，不是展示聊天动画或堆技术名词。
4. 20 项合成任务是可审阅的起点，不是生产代表性证明。当前没有真实批量 A/B 成绩，不能宣称反馈循环优于一次生成。

支持的任务、来源、拆分与审批规则见[评测指南](evaluation.md)；当前真实模型记录仍是首个请求的服务错误，不是修复成功案例。

## 2. 模型与运行时怎样分工

| 角色 | 可以决定什么 | 不能决定什么 |
| --- | --- | --- |
| 模型 | 检索顺序、阅读对象、候选修复、何时尝试公开测试、何时结束候选 | 扩大文件权限、传入任意命令、改验收、增加预算、直接宣布修复通过 |
| 工具运行时 | 参数/路径检查、版本冲突检查、工具执行、结果裁剪、停止与本地产物记录 | 根据某个任务 ID 偷偷注入专属修复答案 |
| Docker 执行器 | 在固定本地镜像中运行允许的测试目标，限制网络/资源并分类结果 | 允许模型改变启动命令、挂载宿主目录或把没有运行测试算作通过 |
| 独立验证器 | 从原始快照另建工作区、重放封存补丁、运行原测试和维护者验收 | 相信模型的完成宣言、信任旧工作树、把模型自写测试当作独立正确性证明 |
| API / Worker / PostgreSQL | 排队、领取、心跳、持久化、查询、取消与有所有权校验的终态发布 | 保证模型或测试只运行一次、自动恢复原模型会话、承诺公网多租户安全 |

模型输出始终是待校验输入。Issue、源码、日志中的“忽略限制”等文字不会修改工具白名单；但这不表示模型不会受到提示注入影响。安全依赖运行时限制，不依赖模型听话。

## 3. 代码结构与阅读入口

| 单元 | 实际职责 |
| --- | --- |
| [task.py](../src/patchpilot/task.py)、[snapshot.py](../src/patchpilot/snapshot.py) | 严格任务格式、固定快照核验、显式公开输入白名单 |
| [workspace.py](../src/patchpilot/workspace.py) | 每次执行复制独立 repo，不复制父目录或答案 |

| [tools.py](../src/patchpilot/tools.py)、[patching.py](../src/patchpilot/patching.py) | 七个工具、严格参数、受控文件操作和差异 |
| [anthropic_model.py](../src/patchpilot/anthropic_model.py) | 官方 SDK 适配、完整流超时、JSON 校验与安全错误分类 |
| [sandbox.py](../src/patchpilot/sandbox.py)、[verification.py](../src/patchpilot/verification.py) | 固定容器执行和从基线重建的独立验收 |
| [service](../src/patchpilot/service) | 本机 API、独立 Worker、六表状态、租约、SSE、产物与恢复 |

API 与 Worker 是同一项目的两个进程，通过 PostgreSQL 协作，不是微服务拆分。CLI 可独立使用，不要求先启动数据库。

## 4. 一次执行的实际顺序

1. `load_task` 检查格式、真实文件布局与快照 SHA-256；`create_workspace` 只复制任务的 `repo/`。
2. `run_agent` 构造公开输入，做一次不计入模型工具预算的初始目录观察。公开输入不含参考补丁或维护者验收。
3. 检查取消、时限、调用次数、上下文和已知 token，再向模型发送历史与固定工具 schema。
4. SDK 适配器先取得完整响应并检查工具 JSON。循环记录完整 assistant content，再检查停止原因、工具 ID 和预算；不边接收参数边执行。
5. 按模型给出的顺序**逐个**处理工具：预算检查 → `tool_started` → `dispatch` 严格参数与操作权限校验 → 执行 → 本地工具证据 → 配对结果与 `tool_finished`。
6. 同轮结果合为一个 user 消息，保留 `tool_use_id` 对应关系；完整批次没有进入终止状态时，通知服务层保存已确认代码边界，再进行下一轮。
7. 合法 `end_turn` 且未被停止机制拦截时，导出并封存候选，调用独立验证器；验收结果不再回流给模型反复试题。
8. 记录结论与候选产物。服务层在所有权校验的事务内发布最终报告、状态与终止事件。

**不是整批工具事务：** 前一个工具可能已修改文件，后一个工具才发现参数非法；参数错误通常作为工具观察返回，后续是否继续取决于循环的终止条件。不是所有工具都要求 workspace hash；`apply_patch` 显式要求 `expected_hash`，读取工具则返回当前摘要供下一次修改使用。

逐行追踪与自测见[执行链讲解练习](execution-walkthrough.md)。

## 5. 为什么暂时不用多 Agent、向量库与复杂编排

### 单 Agent

当前问题首先是能否在受控预算内取得可信补丁。增加“规划者、执行者、审查者”会增加消息协议、调用成本、并发工作树冲突、归因和恢复复杂度，还不能代替独立测试。没有证据表明当前任务需要多决策者，先保留单循环，便于观察失败原因。

以后只有在真实任务显示可分解子问题、存在可量化收益，且能控制共享状态与成本时，才值得评估多 Agent。那是候选方向，不是现有能力。

### 普通文本检索

当前快照很小，`list_files`、分页 `read_file` 与精确 `search_text` 已能找到源码。向量库会引入切块、索引版本、召回评测与依赖运维；向量相似也不能替代精确符号或错误文本搜索。目前没有为它付出复杂度的证据。

### 显式循环与 PostgreSQL

循环只有有限工具和清楚的停止条件，直接写控制流更容易展示协议顺序和失败窗口。后端已经用真实 PostgreSQL 提供持久状态与行锁，不需要为了“像架构”再加 Redis 队列或编排框架。若后续出现跨机器调度、更多工作流和吞吐需求，应重新做需求与收益评估，不能把本机实现描述成现成分布式平台。

## 6. 工具、预算和文件写入的真实保证

### 操作权限

七个工具是 `list_files`、`read_file`、`search_text`、`apply_patch`、`add_regression_test`、`get_diff`、`run_tests`。没有 shell 工具。

- 源码修改限已有 `src/**/*.py`；唯一新增文件例外是 `regression/test_*.py`，不能覆盖已有文件。
- 原 `tests/`、`repro/`、配置、依赖不可改；拒绝越界、链接、删除、重命名、二进制与模式变更。
- 测试只能选公开的预置目标或允许的测试文件；不能传 shell、pytest 参数或 `/acceptance`。
- 参数合法仍不代表操作允许，后续还要校验路径、文件事实和补丁内容。
- 工具结果有长度限制和 `truncated`；模型的文件工具不能读取宿主 artifacts。容器日志本身也有上限，不是无限完整日志。

### 默认 Agent 预算

| 项目 | 默认值 | 含义 |
| --- | --- | --- |
| 模型请求 | 8 次 | 无 SDK 隐式重试，不自动切模型 |
| 工具动作 | 32 次 | 初始目录观察不计入该次数 |
| 总时间 | 180 秒 | 动作检查和网络/测试时限，清理另有宽限 |
| 已知总 token | 100000 | 响应后累计的停止阈值，不是金额硬上限 |
| 单次输出 token | 4096 | 请求上限还受剩余额度限制，不预先精算输入 |
| 上下文 | 120000 字符 | 超过则停止，不静默删历史 |
| 重复行动 | 3 次 | 同版本、同工具及参数的重复累计达到阈值时停止 |

预算属于一次 Agent 执行；新 Attempt 会重新计数，不是跨重启的全局费用封顶。缺 usage 的请求仍可能计费。验收前的预算停止通常保留 `unverified` 候选；已经进入独立验收后耗尽剩余测试时间，可能得到 `timeout`，不要把所有时限路径混成一个状态。

### 不要把 staging 叫成崩溃原子事务

`apply_patch` 在 staging 完成整包检查、应用与 inventory 核对；格式或 Git 校验失败不会修改原工作树。但发布是两次目录 rename，异常时尝试回滚，不提供跨进程锁、崩溃原子交换或磁盘故障事务。

`add_regression_test` 用排他新建防覆盖，但中途写入失败仍可能留下部分新文件。本地 transcript 等记录也不是跨文件原子提交。服务恢复依赖已提交 checkpoint 重新建立工作区，而不是假定每次宿主写入都不可中断。

## 7. 沙箱能防什么，不能防什么

### 当前限制能减少的风险

测试使用预构建本地不可变镜像 ID，运行时不拉取镜像、不安装依赖；没有可用 Docker 时不会回退到宿主执行。

- 非 root `10001:10001`，无网络，1 CPU，256 MiB 内存及交换上限，64 个进程。
- `/tmp` 为 64 MiB、noexec tmpfs；单文件 16 MiB；轮转日志约 1 MiB。
- 丢弃 capabilities，`no-new-privileges`；通过复制文件而非挂载宿主目录传入工作区。
- 不传模型凭据、不挂 Docker socket；默认测试执行时限 30 秒，正常退出路径清理自身创建的容器。

它能减少可信任务意外联网、资源失控、误访问宿主文件及状态串扰。

### 当前不能承诺的防护

- 测试会执行 Python，候选源码可以影响同一 pytest 进程；恶意代码可能篡改 pytest、伪造 JUnit 或读取同一验收环境内的材料。
- 没有只读 rootfs、容器总磁盘配额、虚拟机级隔离或恶意多租户安全保证。
- 模型看到的公开工具边界不等于对能下载整个开源仓库的人保密；维护者验收是“运行中不交给模型”，不是密码学隐藏。
- 宿主被强杀或 Docker daemon 故障时 finally 可能不执行；租约回收默认不批量删除查询到的容器。
- 固定镜像只保证版本可识别，不保证没有漏洞，也不能替代安全更新。

因此只接受自行编写、维护者审核的可信任务，不应开放公网任意仓库执行。

## 8. 验收通过究竟意味着什么

`verify_patch` 只接收补丁字节，从已核验基线另建工作区；报告绑定补丁、base、candidate、维护者验收摘要和实际镜像 ID。验收运行原 `tests`、公开 `repro` 与维护者 `/acceptance`，不拿模型新建的 regression 充当可信评分。

执行器联合退出码和有界 JUnit 分类：必须确有至少一项通过、没有失败/错误且退出码一致。全跳过、零测试、报告缺失或矛盾都不能算通过。

**通过表示：** 这个候选在这组固定材料、这个环境与本次执行中通过了指定行为检查。

**通过不表示：** 全部输入都正确、无安全问题、没有回归、测试覆盖完整、适用于任意仓库，或已经证明模型胜过基线。测试 oracle 本身也需要人工审阅；合成任务的 20/20 参考材料验证不是模型成功率。

## 9. 后端可靠性与崩溃窗口

完整接口见[服务指南](stage4-service.md)。这里强调保证的范围：

1. API 只排队；Worker 用 `FOR UPDATE SKIP LOCKED` 领取。每次领取创建 Attempt 和随机所有权 token。
2. Worker 写入以 Run → Attempt 顺序锁行，核对当前 Attempt、worker、token、running 和数据库时间下未过期的租约。旧 Worker 不能把迟到结果登记为当前结果，但 fence 不能撤销已发模型请求或所有本地文件写入。
3. 最终报告先封存，租约再次校验；报告引用、终态与终止事件在同一个数据库事务中提交。文件系统与数据库不是分布式事务，失败可能留下孤儿文件。
4. 取消与完成按行锁串行决定；已完成提交后到达的取消不能倒转历史。
5. SSE 从数据库事件序号续读，断开连接不会取消执行；进度不是模型思维直播。Step、事件和 checkpoint 不保证与物理工具操作一个事务。
6. checkpoint 保存已确认代码边界的累计补丁与摘要，通常是完整且未终止的工具批次，不是每个工具或每个 token。中途未确认修改会被丢弃。
7. 显式 restart 从 base 新建工作区，校验并应用已确认补丁、检查候选摘要，开启新模型会话与预算。只允许 failed/interrupted；预算停止通常是 completed/not_run，不能直接 restart 同一 Run。

数据库保存六表状态与小型摘要/引用；完整本地 transcript、工具证据和大日志留文件。服务 API 不等于把所有本地证据全部登记开放。当前无跨机器共享存储、自动 GC、完整跨 Attempt 账单或 exactly-once 保证。

## 10. 已知限制与后续门槛

- 真实 API 服务错误尚未取得成功修复证据；无真实批量 A/B、无账单核对。
- 20 项 AI 协助自建任务仍待用户人工审阅；保留集不是严格盲测，不能宣称训练无污染。
- API 仅本机 Bearer 认证，未实现多人隔离、公网限流或公网运营设施。
- 本地 PostgreSQL 测试 schema 按权限要求保留；禁止未核对目标的清理或全局 prune。
- 远程 GitHub CI 尚未实跑；本地验证与远程验证要分开报告。
- 基准资料 MIT 不覆盖整个应用；全局许可证未选择，公开发布仍有法律授权待办。
- 用户负责第35步演示；文档和自动测试不能代替用户自己的讲解验收。

这些限制不是写在结尾的免责装饰，而是决定当前允许输入、允许部署方式以及能够对外宣称什么的实际边界。
