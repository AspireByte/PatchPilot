摘要何时可以替换历史视图？

改变“是否存在安全的旧轮次边界”和“摘要是否有效”，对照请求视图、原始历史与提交结果。

机制怎么工作

一次模型请求先扣除系统提示、工具定义和附加来源的字符开销，再把剩余历史预算交给 HistoryCompactor。默认达到剩余预算的 80% 时尝试压缩，争取降到 60%；60% 是提前结束压缩的目标，最终必须满足字符硬上限。这里比较的是 JSON 序列化字符数，不能当作精确 token 或费用。

压缩从未覆盖的旧历史前缀开始，只在下一条普通用户消息前切分；待配对的工具调用和工具结果不能被切开。默认至少保留最近 6 条消息，并保留当前用户轮。模型只写摘要，内核保存原文范围与摘要对应的 SHA-256；真正发给模型的是“摘要块＋剩余原文”的派生视图。

新摘要先进入局部变量 staged。只有全部校验成功且视图不超上限，才赋值给 self.blocks。因此，摘要失败不会覆盖既有摘要状态，也不会删除原文；已经发出的模型请求仍占用调用、时间和已知用量预算。

同样的“无安全边界”，如果总量仍未超过 10,000，会直接返回原视图，并不会仅因达到触发比例而报错。这里停止的原因是硬上限已被突破。

原文保留；摘要状态不变；不发送超限工作请求。

结果：丢弃本次暂存块，保留上一次已提交的视图

已提交 b1 → staged 中新增 b2 → 后续摘要无效或仍超限 → 抛出异常 → 不执行 self.blocks = staged

本例先前已有已提交摘要 b1，本次有新的旧轮次可压缩；模型生成 b2 后，下一块返回空摘要、过长摘要，或最终视图仍超硬上限。所有本次新增块一起放弃，b1 及其引用继续有效。并非失败前的 b2 也会部分提交。

保留：已提交 b1放弃：暂存 b2 / b3保留：全部原始消息

这是一份摘要状态的提交边界，不是模型调用事务。摘要请求可能已经产生费用；用量未知时保留未知计数。失败后不能把旧视图直接当作已满足本次预算继续调用模型，必须由上层处理停止。

原文保留；既有 blocks 不变；本次请求暂停。

决定分支的代码

以下短片段摘自当前实现，省略中间摘要构建细节：

eligible = [
    n for n in self._boundaries(messages)
    if n <= len(messages) - self.preserve_recent
]
staged = list(self.blocks)
# 摘要生成、长度/缩小效果校验、合并以及最终上限检查
self.blocks = staged

_boundaries 维护待配对工具 ID 集合，只有下一条普通用户消息到来且集合为空，才产出轮次边界。view 校验原文指纹后生成深拷贝；restore 还校验连续范围、合并子块与边界，拒绝原文被篡改后沿用旧摘要。

容易混淆当前实现的边界
达到 80% 就一定变短只有存在新的安全旧轮次，才会生成新摘要；最近内容不能靠删消息强压。
保护最近 6 轮参数单位是消息条数。完整轮次边界与最近窗口共同限制，实际保留可能多于 6 条。
四块后原文被二次覆盖活跃块达到 4 个时尝试合并摘要，原文仍保留；层级最多记为 3，不代表只允许压缩 3 次。
工作模型和评估器发同一个请求共用摘要内核与原文；评估请求另有 JSON 包装和转义开销，会重新核算可用预算。
手动压缩可以越过保护force=True 绕过触发比例，不绕过轮次、最近窗口、配对和硬上限。

记住这一点

压缩修改的是请求视图；轮次边界保护协议，暂存后提交保护摘要状态，原文与引用负责可恢复。这不能保证摘要语义完全无损，也不能替代精确 token 估算。
