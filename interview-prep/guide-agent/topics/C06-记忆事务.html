C06 · 记忆记录与提取游标为什么必须一起提交

切换首次提交、重复投递和并发冲突，观察同一批记忆操作怎样改变记录版本、全文索引、修订历史与提取游标。

机制怎么工作

提取从原始 messages 的已确认游标开始，按消息、内容片段和字符偏移截取有界来源；模型只返回带来源引用和预期版本的 JSON 操作。宿主校验后，用起止游标生成批次 ID，再调用 SQLiteMemoryStore.apply_batch。事务内依次执行：先查批次去重，再比对完整起始游标，再确认位置前进，再写全部记忆及其索引和修订，最后推进游标并登记批次。所有步骤成功才提交。

已处理批次直接返回 False，早于游标比较；新批次遇到游标或记录版本冲突则回滚整批。模型请求发生在事务之外，失败回滚不能退回已消耗的调用预算。SQLite 事务也不包含会话 state.json、事件日志或仓库文件。

这次提交遇到了什么状态？

以下均为机制示意，非实际运行数据。原计划处理原文 m2 到 m4 之前的消息：start=(2,0,0)，end=(4,0,0)，更新主题 A，预期版本为 1。实际游标还携带原文摘要 digest；示意省略摘要内容。每个选项独立展示对应前置状态。

首次提交：记录与游标一同变化

BEGIN IMMEDIATE → 批次未登记 → cursor == start → end 前进 → A v1→v2 → cursor m2→m4 → 登记批次 → COMMIT

返回 True。A 的正文、摘要、FTS 索引与 v2 修订一起写入，游标到 m4，批次被登记。即使提取返回空操作数组，合法的新批次仍可推进游标并登记，表示该段原文已经检查过。

重复提交：去重先于游标校验

BEGIN IMMEDIATE → 找到同一 scope / session / batch_id → 返回 False → COMMIT（无写入）

此前首次提交已经令 A=v2、cursor=m4。本次仍带旧 start=m2，但不会报游标冲突，因为批次去重先执行。A 不升到 v3，游标不重复推进，索引和修订也不重复写。这里演示存储层重复投递；协调器下次正常提取会先读最新游标。

版本冲突：先写的操作也回滚

批次未登记 → cursor=m2 匹配 → 暂写新主题 B → 更新 A 时发现数据库已是 v2、请求仍预期 v1 → ValueError → ROLLBACK

假设别的会话已更新 A，却没有改变本会话游标。本批先写入 B，再碰到 A 的版本冲突，整个事务回滚：B 不保留，A 仍为并发更新后的 v2，本会话游标仍在 m2，批次不登记。FTS 与修订表也回滚；不会留下“原文已处理，但记忆只写一半”的状态。

游标冲突：记忆操作尚未执行

批次未登记 → 数据库 cursor=m3，但 start=m2 → ValueError → ROLLBACK

这是新批次，所以不能命中去重。存储层比较整个游标对象（包括 digest），发现与开始提取时的状态不同，直接拒绝；A、索引、修订均没有被本批修改，游标保留已经确认的 m3。后续处理需要重新取得游标和原文；本次调用不会自动覆盖水位或无限重试。

召回快照与原文提取分开

召回在一轮开始时将全局偏好与当前项目搜索结果组织为有界、不可变的摘要快照，注入请求。全文搜索使用 SQLite FTS5 与 BM25 排序；本项目没有向量检索实现。需要正文时，工作模型使用只读记忆工具分页读取。

提取读取原始消息而非压缩摘要或召回快照；跳过记忆工具返回的内容，避免记忆回流成为新的来源。位置由 message / part / offset 描述，digest 校验原文引用；这不是逐 token 的后台线程。正常回答完成后同步处理一批，也可通过显式命令处理下一批，单批受来源片段与字符预算限制。

全局自动记忆只接受用户明确表达的偏好；成功经验还需当时成功的命令或检查证据。来源校验缩小无依据写入的范围，但不能保证模型摘要语义完全正确。记忆始终是历史数据，不授予执行权限，也不能替代本次测试。

回答完成，不代表记忆一定写入

AgentSession._finish_answer 先保存会话，再尝试提取；提取异常记录为记忆错误，已经生成的主回答仍可返回。游标保留旧位置，后续可从该处重新处理。若已用掉模型调用或 token，数据库回滚也不会撤销用量。

用户遗忘会留下墓碑，迟到的自动批次遇到同主题墓碑时跳过该项，仍可提交其余合法操作并推进游标；显式手动记忆才可恢复该主题。历史会话与修订仍保留，因此“忘记”表示停止召回，并不等于物理擦除全部历史。

记住这一点

游标表示哪些原文已处理：它必须与整批记忆写入共用一个事务；同批次先去重，新批次再校验游标和版本，失败时两边都不推进。
