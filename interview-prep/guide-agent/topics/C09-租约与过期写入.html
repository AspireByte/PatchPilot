C09 · 旧 Worker 为何失去提交权

切换结果提交的时刻，对照当前执行尝试、数据库时间与租约，理解领取互斥、执行权续期和过期写入隔离分别解决什么问题。

机制怎么工作

领取 queued 任务时，Repository.claim 在短事务中用 SELECT FOR UPDATE SKIP LOCKED 锁住一个 Run，创建 Attempt、生成随机 token，并更新 current_attempt_id。事务提交后释放行锁，模型和工具在事务外执行。之后每次受保护写入都重新经过 _fence：先按 Run → Attempt 的顺序加锁，再读取数据库 clock_timestamp()，核对当前 Attempt、运行状态、Worker、随机 token 和未过期租约。

心跳同样先经过 _fence；租约已经过期时，原 Worker 不能靠迟到心跳重新获得执行权。这里使用随机身份凭据加数据库状态校验，并没有单调递增 fencing token。数据库写入校验也不能撤销已发出的模型请求、费用或全部文件系统副作用。

旧 Worker A 在哪个时刻提交？

以下时间和 A/B 标识均为示意。t=0 时 A 领取任务，Attempt=A，租约截止 t=15；A 随后停止心跳。忽略取消请求，提交表示尝试登记最终报告和终态。

租约有效 · t=10

Run=running → current_attempt=A → Attempt=running → Worker/token 匹配 → 10 < 15 → 允许继续提交

在 report_factory 前的校验通过。报告写入后还会再次读取数据库时间并校验；若第二次也未过期，报告引用与最终状态在同一数据库事务中提交。只通过第一次检查，仍不足以保证最终登记成功。

租约已过期 · t=16

Run=running → current_attempt=A → 身份仍匹配 → 15 ≤ 16 → LeaseLost → 拒绝写入

即使回收器尚未执行、数据库仍显示 running，时间条件已经使 A 失去执行权；finalize 会在报告回调之前拒绝。reap_expired 随后把未取消的 Run/Attempt 标成 interrupted，租约清空；它不会自动把任务重新排队。

重启并重新领取 · t=18

A 过期 → reap_expired 标为 interrupted → 显式 restart 变 queued → B 再次 claim → current_attempt=B → A 提交被拒绝

restart 本身把 current_attempt_id 清空并保留 latest_checkpoint_id；随后 claim 才创建新的 Attempt 和随机 token。A 的提交在第一层当前 Attempt 校验就失败，无需等待新租约到期。新 Worker 可从已登记的补丁检查点重建候选仓库；这不等于恢复完整聊天历史或自动重放所有工具。

数据库拒绝写入，不等于外部动作自动回滚

Worker 的心跳线程遇到租约丢失或数据库异常会设置停止信号，执行路径在协作检查点观察取消。但远端请求可能已经发出，本地产物也可能已封存。数据库事务保护报告引用、事件和运行状态的登记，不能把这些外部动作一起回滚。

finalize 在报告回调前校验一次，写完小文件后再校验一次。若文件写入期间租约耗尽，第二次检查拒绝登记并回滚数据库事务；文件系统中可能留下未公开登记的产物。取消请求在锁内还能把拟提交的成功结果改为取消终态，避免迟到成功覆盖取消。

记住这一点

SKIP LOCKED 负责短事务领取；心跳续期负责维持执行权；每次写入的当前 Attempt、随机 token 与数据库租约校验负责拒绝旧执行者。过期后要显式 restart，再次 claim 才会产生新 Attempt。
