# C10 评测与工程质量：统计全部尝试，区分失败与未知

> 课程性质：核心
> 返回：[导学](../PatchPilot/导学.md)；前置：[C08](08-代码验证与证据.md)、[C09](09-任务服务与租约.md)；下一步：[面经](../PatchPilot/面经.md)。
> 对应：B5；[Q7](../PatchPilot/面经.md#q7-agent-评测怎样避免自我证明)；目标掌握：理解机制、设计与表达。

## 本课重点

计划 10 次尝试，其中 3 次通过、2 次环境失败、1 次未完成时，不能删除失败再声称高成功率。项目先冻结评测计划，再逐项保存结果，主分母包含全部计划尝试；能力相关的条件指标另列，避免混淆端到端体验与模型修复能力。

当前材料没有运行真实模型评测，也没有生产成功率与性能数据。已有测试能帮助定位宿主逻辑保证，真实 API、Docker 和 PostgreSQL 环境仍需要各自的执行证据。

## 主链与职责

`数据集/任务版本 → BatchConfig 计划 → 每个 task×strategy×repeat → baseline 或 Agent → 独立验收 → 单次记录 → load_records 补全未完成位置 → summarize → JSON/Markdown 摘要`。

任务、验收、镜像、配置、代码、数据集摘要和实际服务模型信息用于判断配对是否可比较。只比较名字相同的任务不足以证明实验条件一致。

## 源码阅读

先读 [evaluation/runner.py](../../src/patchpilot/evaluation/runner.py) 的 `BatchConfig / AuditedModel / load_records`，确认计划和实际响应怎样保存。再读 [baseline.py](../../src/patchpilot/evaluation/baseline.py) 的 `run_baseline`，它是用于对照的固定提示/检索策略，不读取参考答案来生成真实 Agent 成绩。最后读 [metrics.py](../../src/patchpilot/evaluation/metrics.py) 的 `_group / summarize / estimate_cost / known_usage_cost`。

主指标的实现非常直接：

```python
total = len(rows)
passed = sum(row["status"] == "passed" for row in rows)
# success_rate = passed / total
```

关键在于 rows 由计划槽位恢复，未完成记录不会消失。`summarize` 还拒绝重复 task/strategy/repeat 槽位，避免重复加载使分母失真。完整分母同时报告 failure_category，才能解释环境失败与代码修复失败的区别。

## 机制与边界

`paired` 仅将同版本条件且失败类别可评分的配对计入方向胜负；环境错误、截断、模型不匹配等使配对不可比，但仍留在端到端主分母。多次重复报告“所有重复通过”与“至少一次通过”，两者都不应自动称作特定采样假设下的 pass@k。

费用按显式模型/币种/价格版本乘已知输入、输出和缓存用量，用 Decimal 避免浮点误差。未知 usage、缺缓存单价、实际模型不匹配时，总费用保持未知；可单列部分已知费用。单次成功成本与“全部尝试费用/成功数”不同，后者要包含失败尝试的费用。估算也不等于服务账单。

工程质量分层：核心循环用假模型验证协议与计数；文件工具验证路径和冲突；压缩验证边界、回滚与恢复；记忆验证来源、事务和水位；进程/Harness 验证清理与证据；数据库服务需要真实 PostgreSQL 并发语义；Docker 集成需要真实引擎与本地镜像。SQLite 无法替代 PostgreSQL 行锁/时钟语义的验证。

## 需要懂什么

评测必须把“计划做什么”和“实际得到什么”分开，失败与未知本身就是结果。只对成功样本求均值会有幸存者偏差；只展示某次最优运行会隐藏方差。当前代码报告描述统计，小型合成任务和相关重复样本不能支持生产外推或统计显著性结论。

如果要评估压缩/记忆的真实收益，应固定模型、任务与预算，对照开关条件，同时记录最终验收、约束遗失、token、耗时与未知用量；这是未来评测方案，当前不作为已完成实验写进简历。

## 需要记住什么

- 主分母＝全部计划尝试；条件能力指标单列，环境失败不删除。
- 对照须核对任务、验收、模型、镜像、代码和配置版本；不匹配不记方向胜负。
- 未知费用不记零，已知费用不冒充总账单；独立验收与模型自述分开。
